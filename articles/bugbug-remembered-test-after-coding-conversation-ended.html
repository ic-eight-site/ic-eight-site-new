BugBug Remembered the Test After the Coding Conversation Ended

Product Value Evaluation #050 · Published September 2026

BugBug’s value became clearest when the application itself was not broken.

The test had already passed twice against an isolated Signal Shelf flow. The only change was inside BugBug: the final expected article title was replaced with a title that did not exist. On the next run, BugBug waited for the assertion, failed at that step, and showed both the false expected value and the correct text that was actually present on the page. It also exposed a character-level diff, an ASSERT_FAILED error, a screenshot of the failed state, a DOM snapshot, and an option to download the HAR network log.

That controlled failure mattered because it separated two questions that browser testing tools often blur for non-specialists: whether the application is wrong, and whether the test is wrong. In this case, the application had not changed. The failure evidence made it possible to see that the expectation was the problem.

The same test then returned to passing after one assertion value was restored. It did not need to be re-recorded or rebuilt.

For this evaluation, that persistence was more important than the fact that BugBug could replay browser clicks. A coding agent can also open a browser after a change and check whether something still works. BugBug added a durable test asset that remained available outside that coding conversation, together with its selectors, exact assertion, run history, failure evidence, and an exportable YAML representation.

Whether that makes BugBug worth operating is a separate question.

Key Findings

  • BugBug recorded one representative Signal Shelf workflow as a nine-step browser test without handwritten test code or manually authored selectors. The unchanged test passed twice, in 13.59 and 13.38 seconds.
  • Changing only the final expected text produced a controlled failure after 44.54 seconds. The failed assertion showed the expected and observed values, a character-level diff, ASSERT_FAILED, and a 30-second timeout, while the application itself remained unchanged.
  • Restoring the correct expected text in the existing assertion returned the same test to a passing state in 15.28 seconds without re-recording.
  • The saved test persisted as more than a replayable sequence inside the editor. Runs history retained the normal passes, controlled failure, and repaired pass, while YAML export preserved the nine ordered actions, generated selectors, waiting-condition settings, and restored assertion in a readable external file. Import and round-trip fidelity were not tested.
  • The product required a Chrome extension and incognito enablement before local recording and execution. The account was also inside a 14-day advanced-feature trial rather than a pure Free-plan environment.
  • For the current occasional site-update workflow, the post-test judgment was that this persistent test system would probably not be used often enough to justify maintaining another extension and separate tool. Scheduled execution made the product model more compelling, but schedules and alerts were not tested and current official pricing placed them above the Free plan.

Evaluation Setup

The evaluation used one approved simulated persona: a solo product owner who uses AI coding assistance but does not personally maintain browser automation code.

The test application was an isolated local copy of Signal Shelf. The selected workflow was deliberately narrow: search for one known article, open it, save it, return to the article list, open Saved, and confirm that the exact article title appeared there.

Before BugBug recording began, that workflow was manually verified and the article was unsaved again so the recording would start from a clean state. The application files were kept unchanged throughout the controlled-failure portion of the test.

Testing took place in Chrome with an English interface from Brazil. The BugBug account began in a 14-day advanced-feature trial that stated it would downgrade automatically to Free without requiring a payment method. A Chrome extension and incognito access were required before local recording or execution could proceed.

The evaluation did not test cloud execution, schedules, alerts, integrations, MCP, CI/CD, visual regression, responsive-browser execution, selector durability after redesign, or long-term maintenance.

A Browser Flow Became a Persistent Test

BugBug recorded the representative flow as a nine-step test named Save article to Saved Items. The final visible step asserted that the saved article text was exactly The Cost of One More Setting. BugBug generated the selector used by that assertion; the evaluator did not write a CSS or XPath selector manually.

Two unchanged local runs then passed in 13.59 and 13.38 seconds. Those two runs are not enough to support a broad reliability claim, but they were sufficient for the purpose of the experiment: the recorded sequence could be replayed against the same controlled application and reach the expected result twice.

This is where BugBug began to differ from a one-time browser check performed inside a coding conversation. The flow now existed as a named test with explicit steps and an explicit expected outcome. It could be run again without reconstructing the request in a new prompt or relying on the previous coding session to remember exactly what had been checked.

The Controlled Failure Made the Test Easier to Reason About

The most informative run came after the final assertion was deliberately made false.

Only the expected value changed, from the real title to Article That Does Not Exist. Signal Shelf itself was left untouched.

The resulting run failed at the intended final step after 44.54 seconds. BugBug showed the false expected text alongside the actual page text, The Cost of One More Setting, and included a character-level diff. The error was labeled ASSERT_FAILED, with a 30-second timeout. The run details also retained a full browser screenshot of the failed step and exposed a DOM snapshot and HAR download option.

The 44.54-second duration should not be read as a typical failure time; most of it came from waiting for an intentionally impossible assertion to time out.

What mattered was the diagnosis. A non-specialist did not need to inspect the application source to understand what had happened. The page still contained the correct title, while the test expected something that was not there. The evidence therefore pointed to a broken expectation rather than a broken application.

That distinction is more useful than raw automation alone. A browser test that merely says “FAIL” still leaves substantial interpretation work. Here, the failure record contained enough context to explain why it had failed.

Repair Did Not Require Rebuilding the Flow

The evaluator then edited the existing assertion and restored the correct expected text.

No new recording was needed. The rest of the nine-step test remained intact, and the repaired run passed in 15.28 seconds.

This was a deliberately narrow repair, so it does not establish that BugBug tests are generally inexpensive to maintain. A real interface redesign could invalidate selectors or require larger changes.

Within this experiment, however, the test behaved like a maintainable asset rather than a disposable recording. One expectation was wrong, one expectation was corrected, and the same test returned to a passing state.

What Persisted Beyond the Coding Conversation

The strongest difference from an ad hoc Codex browser check was not that BugBug could operate Chrome. It was that the test remained inspectable after the original task was over.

Runs history retained the two normal passes, the controlled failure, and the repaired pass. The editor retained the recorded steps, generated selectors, waits, and assertion configuration.

The test could also be exported as YAML. The exported file contained the local starting URL, nine ordered actions, generated XPath selectors, waiting-condition overrides, and the repaired expected text.

That export makes the test readable outside BugBug’s visual editor and potentially versionable with other project artifacts. The evaluation did not re-import the YAML, so it does not establish round-trip fidelity.

A coding agent can already run repository tests and browser checks after a change. BugBug’s added value in this experiment was narrower: the browser expectation itself became a persistent object that did not depend on the coding conversation remaining available or on a future agent being told exactly what to check again.

Persistence Also Creates Operating Overhead

The same persistence that creates value also creates another system to maintain.

Local use required the BugBug Chrome extension and incognito enablement. The product added its own project, test, run-history, and configuration layer alongside the existing development workflow.

For a team that exercises the same important browser flows repeatedly, this may be a reasonable cost. For a solo operator making occasional site updates, the economics are less obvious.

The post-test judgment in this evaluation was not that BugBug had failed or was difficult to understand. The test itself worked well. The issue was frequency. If a browser check is only needed occasionally, asking a coding agent to perform a focused verification after each change may be simpler than maintaining another persistent test environment.

The evaluator understood the convenience of persistent and scheduled testing, but still could not identify a recurring task in the current occasional site-update workflow that would justify maintaining BugBug.

That adoption judgment is specific to the current workflow and should not be generalized to teams with a larger regression surface or more frequent releases.

Scheduled Execution Could Change That Calculation

The evaluator later reported receiving a welcome email that foregrounded the phrase “Schedule your tests.” That message made the broader automation model more legible, but the email itself was not treated as direct product-behavior evidence.

The distinction is straightforward. A saved test is useful if someone remembers to run it. A scheduled test becomes more valuable when the point is to check something repeatedly without waiting for a human to request the next run.

BugBug exposed Schedules and Alerts during the advanced-feature trial. Current official pricing, rechecked on September 19, 2026, documented local runs and core recording/history functions on Free, while cloud runs, schedules, and alerts were assigned above Free.

No schedule, cloud run, email alert, webhook, or Slack notification was executed in this evaluation. Scheduled execution therefore remains an adoption hypothesis rather than a demonstrated result.

For the current operator, however, it provides a plausible threshold. If the job changes from “check this after I edit the site” to “keep checking this flow every day or every week whether I remember or not,” a persistent browser test becomes easier to justify.

Implications

BugBug demonstrated the representative task clearly. One browser workflow became a repeatable test, the deliberately broken expectation produced understandable evidence, and the repair required changing one field rather than reconstructing the flow.

The more interesting question was not whether the product worked, but when that durable test becomes preferable to an agent-run check requested on demand.

For occasional site updates, the answer remained uncertain because the dedicated test system introduces extension setup and ongoing maintenance for a workflow that may not recur often enough to benefit from persistence. For repeated or unattended checks, the balance may change, especially if scheduled execution and alerting become part of the requirement.

That latter case was not tested here.

Evidence and Limits

This evaluation covered one purpose-built local application and one stable browser flow. It included two normal passing runs, one deliberately broken expectation, and one repaired passing run. It does not establish general reliability, regression prevention, selector resilience after UI changes, or long-term maintenance cost.

The controlled failure was created by changing the test expectation, not by introducing an application defect. The article therefore does not treat it as evidence that BugBug detected a real regression.

The failed run’s screenshot remained available in BugBug’s run history but was not available as a local publication asset in the writing kit.

YAML export succeeded, but import and round-trip fidelity were not tested.

The account was inside an advanced-feature trial. Trial-visible features should not be interpreted as Free-plan entitlements. Current official pricing was rechecked on September 19, 2026 and would need to be checked again if publication were delayed.

Cloud runs, schedules, alerts, integrations, MCP, components in real workflows, Testing Inbox, visual regression, multiple tabs, popups, iframes, CI/CD, custom profiles, and responsive-browser execution were not behaviorally tested.

No claim is made that BugBug replaces QA, is faster or cheaper than coding-agent verification in general, or reduces production incidents.

Finding the gap is only half the work. The other half is deciding what to do about it.
